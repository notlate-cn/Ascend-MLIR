什么是 AI-First 开发

传统开发方式
  • 工程师读文档 → 理解 API → 写代码
  • 遇到 Bug：加断点、printf、查 Stack Overflow
  • 知识积累在工程师头脑中，会话间断层
  • AI 是"辅助工具"：偶尔问问，粘贴代码片段
  • 工程师是"执行者"，决策和实现都在人脑
AI-First 方式
  • 工程师描述意图 → AI 读代码 → AI 生成实现
  • 遇到 Bug：AI 在容器中执行测试 → 分析 IR 输出 → 定位根因
  • 知识积累在 CLAUDE.md + Memory 系统中，永久保留
  • AI 是"协作者"：持有完整项目上下文，主动发现问题
  • 工程师是"架构师 + 评审者"，聚焦高层决策
不是让 AI 替代工程师，而是让工程师用 AI 突破认知边界——在没有社区先例的领域，靠 AI 的代码推理能力快速建立认知

编译流水线架构

整条架构由 AI 在单次会话中规划（2026-01）
流水线阶段
Step 0  linalg-on-tensor 输入 IR
↓ tile + fuse
Step 1  分块后的 linalg 循环
↓ transform dialect 变换
Step 2  transform 脚本驱动的变换
↓ one-shot-bufferize
Step 3  memref-based IR（带 scf.for）
↓ ascendc-buffer-placement
Step 4  片上内存空间标注（TPosition）
↓ linalg-to-ascendc-compute
Step 5  AscendC 向量/矩阵 Op
↓ prepare-for-emit + parallelize
Step 6-8  最终 C++ 内核代码
两个关键 Pass
AscendCBufferPlacementPass
--ascendc-buffer-placement
推断每个 memref 的片上位置（TPosition）。通过循环注解（prologue/epilogue）识别计算区域，应用规则推断 CO1/VECIN/VECOUT/VECCALC，然后向 subview 传播，最后插入 memref.copy 占位符。
LinalgToAscendCComputePass
--linalg-to-ascendc-compute
将 linalg.generic / matmul / fill 转换为 AscendC 的 duplicate_l2 / add_l2 / max_l2 / gather_l2 等 Op，通过 asc.tbuf.get_tensor 桥接 memref 与 local_tensor 类型。
另有 AscendCPrepareForEmitPass（TilingData 生成、flat pointer 计算）和 AscendCParallelizePass（多核并行化）两个后处理 Pass。

案例1：流水线架构规划

用户的原始请求
我需要把 linalg.matmul + linalg.add + linalg.max（relu）做成完整的 AscendC 内核。PyAsc 方言有哪些 Op 可以用？怎么映射？
从 PyAsc 的 TableGen 定义看，有以下核心 Op 可用，对应关系如下：
AI 推导的 Op 映射表
linalg op条件ascendc op
linalg.fill memory_space > 0 duplicate_l2
linalg.matmul A∈A2, B∈B2, C∈CO1 construct + set_tensor_a/b + iterate_all
linalg.elementwise add dst memory_space > 0 add_l2
linalg.elementwise max dst > 0, src1 是零填充 max_l2（ReLU 模式）
AI 的关键分析
memref → local_tensor 桥接
AscendC compute ops 需要 !ascendc.local_tensor<*xT> 类型，不能直接用 memref。对于 memref<..., pos:i32>，需要先生成：
%tbuf = asc.tbuf : !ascendc.tbuf<pos> %tensor = asc.tbuf.get_tensor %tbuf : !ascendc.tbuf<pos>, !ascendc.local_tensor<*xT>
矩阵乘需要 TQue 管理
matmul 的 construct/set_tensor/iterate_all 三步需要与 TQue 生命周期绑定，AI 建议将这部分推迟到 PrepareForEmit Pass 统一处理，不在 Compute Pass 中完成。
AI 无需运行任何代码，通过阅读 TableGen 定义推导硬件 API 的语义约束，建立完整的 Op 映射体系

真实对话片段（代码实现过程中 AI 的主动汇报）

案例2：单次会话实现完整编译 Pass

Pass 功能
推断 bufferized IR 中每个 memref 的片上位置（TPosition），将整数 memory_space 属性注入到 memref 类型中，为后续 AscendC Op 转换做准备。
关键挑战
  • PyAsc TPosition 类型系统完全不透明
  • 没有文档说明 memory_space 如何编码
  • 测试框架的基础假设可能是错的
  • 需要从 TableGen 源码推断正确格式
关键对话：发现根本性错误
测试期望 #ascendc.gm 格式，但 IR 里没有出现这个格式，输出的 memref 类型看起来很奇怪...
找到问题了。TPositionAttr 是 I32EnumAttr，不是 AttrDef，没有 mnemonic。测试用例里写的 #ascendc.gm 是完全错误的格式。

memory_space=0 不打印（因为 0 是默认值，MLIR 约定省略），1 会打印为整数。所以 TPositionAttr 作为 memory_space 会被打印为整数。

正确格式：memref<4xf32, 1:i32>，而 GM 的 memref<4xf32> 省略不写。
这一个洞察消除了整个测试框架的根本性假设错误，避免了数天的无效调试

案例3：476 轮追踪 5 个级联 Bug

AI 通过 SSH 在 Docker 容器中执行构建，将 IR 输出与预期对比，逐步缩小问题范围
1
动态 alloc 缺少操作数 — createLocalMemref 创建带 ? 维度的 memref 时未提供动态尺寸 Value，导致 verifier 拒绝 IR
2
posMap 键失效 — updateAllocMemorySpace 擦除旧 AllocOp 后，posMap 中的 Value 指针悬空，后续查找返回错误结果
3
subview 传播顺序问题 — CO1 alloc 在替换前已运行传播，导致其子 subview 未继承 memory_space，形成空洞
4
需两轮不动点迭代 — 单次传播不足；必须在 updateAllocMemorySpace 之后再次运行 subview 传播
5
步骤执行顺序错误 — Step 7b 在 Step 8b（alloc 提升为函数参数）之前运行，resolver 找到 %alloc 而非 BlockArg，导致后续 set_global_buffer 未被替换
✓ 8 种 TPosition 全部正确推断，所有测试通过

案例3续：posMap 键失效的推理过程

AI 的代码逻辑推理（直接定位根因，无需运行调试器）
// Bug #2：updateAllocMemorySpace 中的 Value 生命周期问题 // 原来的代码（有问题）： auto newAlloc = rewriter.create<memref::AllocOp>(...); // 创建新 alloc rewriter.replaceOp(oldAlloc, newAlloc); // 删除旧 alloc // ❌ 此时 posMap[oldAlloc.getResult()] 的 key 已失效 // oldAlloc 已被 erase，Value 指向已释放内存 // 后续通过 posMap 查找 newAlloc 的位置信息 → 找不到 → 返回默认 GM // 修复（在 replaceOp 之前更新 posMap）： auto pos = posMap[oldAlloc.getResult()]; // 先读出位置信息 auto newAlloc = rewriter.create<memref::AllocOp>(...); posMap[newAlloc.getResult()] = pos; // ✓ 先建立新映射 posMap.erase(oldAlloc.getResult()); // ✓ 再删除旧映射 rewriter.replaceOp(oldAlloc, newAlloc); // ✓ 最后替换 Op
为什么难以调试
MLIR Value 是 C++ 指针包装，Op 被 erase 后内存可能被复用，posMap 查找可能返回随机结果而不是 crash
AI 的优势
通过代码逻辑推理直接定位，无需 gdb 断点或 AddressSanitizer，节省大量调试时间
这类 C++ 生命周期 / MLIR Value 失效问题极难用传统手段调试，AI 通过静态代码推理直接找到根因

案例4：一个错误的步骤顺序，引发四层级联失败

级联失败链
根因：Step 7b 在 Step 8b 之前运行
↓
resolver 遇到 %alloc（非 BlockArg），返回 null
↓
arith offset ops 已被创建（dead code 残留）
↓
set_global_buffer 未被替换，仍在 IR 中
↓
subview 残留到 ascir-translate 阶段
↓
ascir-translate 遇到未知 Op，报错退出
修复方案（交换两行顺序）
// 修复前（顺序错误）： runStep7b(func); // ❌ subview → set_global_buffer runStep8b(func); // ❌ 提升 GM alloc 为函数参数 // 修复后（交换顺序）： runStep8b(func); // ✓ 先提升 GM alloc 为函数参数 runStep7b(func); // ✓ 再做 subview → set_global_buffer
AI 的定位方法：差分分析
matmul 场景成功 vs broadcast 场景失败。对比两个场景的 IR 差异，发现 broadcast 多一个 alloc 需要被提升。由此推断是步骤顺序问题，而非代码逻辑错误。
AI 通过"差分分析"定位问题：对比成功/失败场景的差异，而不是直接看报错信息

案例6：从零构建 NPU Kernel 仿真执行流水线

背景：已有 PyAsc 的 asc.lib.runtime 可以仿真执行 NPU Kernel，但依赖 PyAsc 内部机制。目标：为自己生成的 Kernel 实现一套完全独立的仿真执行链路。
用户的原始需求（Prompt 节选）
我现在想仿照 PyAsc 的 asc.lib.runtime 将我自己生成的 kernel 在 CPU 上进行仿真执行。

已有三个变量：
tiling_def — tiling data 的 C++ 结构体定义
host_tiling — 在 host 上计算 tiling 参数的 C++ 代码
op_kernel — 实际的 AscendC kernel C++ 代码

请帮我处理，通过 ssh xvm@orb 连接到本机 Docker 环境实际调测。
最终实现：4 步完整流水线
① 生成源码 — ascgen.py 调用 call_ascgen 生成三元组
② 编译 host tiling — compiler.py 调用 g++ 动态编译 C++ tiling 代码，ctypes 加载 .so 计算出具体参数
③ 编译 device kernel — compiler.py 调用 bisheng 编译器生成 ELF binary
④ 仿真执行 — executor.py 用 ctypes 直接调用 libruntime_camodel.so，无需 PyAsc
AI 的关键贡献
逆向工程 PyAsc runtime 机制

案例7：批量补全 PyAsc 方言 Op 定义

背景：PyAsc 方言的 Op 定义不完整，大量 AscendC API 没有对应的 TableGen 定义。需要从4个 C++ 头文件目录中提取所有 API，按规则补充到方言中。

请从以下4个目录中，帮我整理出所有 AscendC API，并补充到 PyAsc 的基础 Op 定义中：

v5102/.../ascendc/api_regbase/

• 函数带 __aicore__ inline 修饰

AI 的三种工作模式

🔍
探索推理模式
当遇到不熟悉的 API 或 TableGen 定义时，AI 通过阅读源码推导语义——无需运行代码，通过静态分析建立理解。

典型场景：TPositionAttr 编码发现、MatmulConfigAttr 参数分析、PyAsc Op 语义推断
🔧
执行验证模式
通过 SSH 在容器中执行构建和测试，获取真实的 IR 输出或错误信息，与预期对比后迭代修复。

典型场景：5 个级联 Bug 的调试、BufferPlacement 测试验证、端到端流水线测试
🏗️
架构设计模式
基于对整个代码库的理解，提出系统性的设计方案或发现潜在的架构问题，主动指出风险和改进方向。

典型场景：流水线架构规划、transform 污染发现、Concat/Gather 的无原语设计方案
三种模式往往在同一会话中交替出现——AI 会根据任务性质自动切换，而不需要工程师显式指定使用哪种方式
在整个项目中，探索推理用于理解新 API 和建立基础知识；执行验证用于 Debug 和正确性确认；架构设计用于处理复杂的系统性问题和新场景接入。

这个 offset 计算对吗？
是的，完全正确。

v56 = v43 * v26 = row * N，这是 output[row*N] 的 flat index，即 output[row, 0:N]。

Op2 写到 v6 + v94*v26，其中 v94 = v77 + v25 = row + M，所以 offset 是 (row+M)*N = output[(M+row)*N]，即 output[M:2M, :]。

两个算子的输出在内存中直接相邻，Concat 语义自动正确，无需额外操作。
AI 持有整个编译过程的上下文：从原始 IR 的 tensor.insert_slice 语义，到 bufferization 的 subview offset，到 flat pointer 计算，到最终 C++ 代码的变量含义——形成了完整的端到端理解链

适合与不适合 AI-First 的任务

适合 AI 的任务
✓ 探索不熟悉的 API — 从 TableGen 定义推导语义，建立初始理解
✓ 实现有明确规范的 Pass — 把设计文档转为 C++ 实现
✓ 多文件数据流追踪 — 跨 .cpp/.h/.td 文件的 Value 生命周期分析
✓ C++ 生命周期 Bug — MLIR Value 失效、指针悬空等静态推理
✓ 级联失败根因分析 — 从报错信息反推根本原因
✓ 测试用例编写 — 根据 Pass 语义生成完整 FileCheck 测试
AI 独立完成较难的任务
✗ 运行时硬件行为验证 — 需要在真实 NPU 上执行，AI 无法模拟
✗ 性能调优 — tiling 参数、内存访问模式需要实测数据
✗ 开放性需求澄清 — "做一个好的编译器"需要工程师定义目标
✗ 前所未见的新型 Bug — 没有先例的错误模式，需要实验定位
最佳分工：工程师负责需求定义、架构方向和最终评审；AI 负责代码实现、API 探索和 Bug 推理

最佳实践 6 条

1
维护 CLAUDE.md 作为"项目大脑"
把架构决策、已知约束、硬件 API 参考表都写入 CLAUDE.md。AI 每次对话自动获得完整上下文，无需重复解释项目。
2
让 AI 能执行，而不只是"建议"
配置好 SSH 访问和构建环境，让 AI 直接运行测试获取真实输出。"AI 说这个方案可行" 远不如 "AI 运行后测试通过" 可信。
3
把重要发现及时固化到 Memory
每次 Bug 修复或重要发现后，更新 MEMORY.md。记录具体的函数名、行号、容易混淆的 API，避免下次重走弯路。
4
用差分分析代替盲目调试
遇到 Bug 时，找一个成功的对照案例。让 AI 对比成功/失败两个场景的差异，往往比直接看报错信息更快定位根因。
5
接受 AI 的主动发现
当 AI 在完成任务时"顺便"发现架构问题，不要认为是跑题。这往往是最有价值的输出。建立机制及时决策和记录。
6
工程师聚焦高层意图，不要逐行指定实现
描述"我需要把 linalg.generic 转换为 AscendC gather"比"在第 370 行添加一个 if 分支"更有效。给 AI 足够的设计空间，往往得到更简洁的方案。

工程师如何验收 AI 的结果？

AI 生成代码不等于正确代码。验收是 AI-First 工作流中工程师不可缺席的环节，分为三个层次：
① 编译验证（即时）
最基础的门槛：能否编译通过
AI 生成 C++/TableGen 后，立即在 Docker 容器中执行构建，编译错误直接反馈给 AI 继续修正
✓ 构建成功 = 语法正确
✗ 不代表语义正确
② IR 输出比对（核心）
本项目最主要的验收手段
每个 Pass 运行后输出 MLIR IR，工程师人工阅读 IR，确认关键节点（memory_space、op 类型、索引映射）是否符合预期
✓ IR 语义可直接阅读
✓ 异常一眼可见
③ Lit 测试（回归保障）
使用 LLVM FileCheck 写断言
每个新功能配套 .mlir 测试文件，用 // CHECK: 锁定关键输出，后续修改自动回归，防止 AI 改坏已有功能
✓ 防止回归
✓ AI 也能写测试

为什么是 Claude Code + Sonnet 4.6？

🏆
市面上同类工具（OpenCode、Codex CLI、Cursor Agent 等）在工具层上功能接近，但 Sonnet 4.6 的模型能力是当前公认最强的编程模型——更长的推理链、更准确的代码生成、更少的幻觉。工具 × 模型，缺一不可。
Sonnet 4.6 的模型层优势
🧠 超长上下文推理 — 200K token 窗口，整个编译器 Pass 的代码一次性读完，无截断
🔬 深度语义理解 — 读 TableGen 推断 C++ API 约束，读 IR dump 追踪数据流，不依赖文档
🎯 精确代码生成 — 生成的 C++/TableGen/Python 极少出现语法错误，减少无效编译循环
🔗 多步推理链 — 5个级联 Bug 的调试，每步推理基于上一步结论，不会在中途"断链"
Claude Code 的工具层优势
📁 原生文件系统访问 — 直接读写项目文件，无需手动粘贴，模型始终看到最新代码
⚙️ 直接执行命令 — SSH 进容器构建、运行 lit 测试、查看 IR 输出，闭环在一个工具内
📚 CLAUDE.md 自动注入 — 项目约定、硬件规格、已知 Bug 列表，每次会话自动加载
🧩 MCP 插件生态 — serena 语义检索、firecrawl 文档抓取，感知能力可自由扩展
🎮 Remote Control — 会话共享、远程协作，超出传统 AI 助手边界

网页版 AI（ChatGPT/Claude.ai）
每次手动粘贴代码 · 无法执行命令 · 会话结束即遗忘 · 适合一次性问答
